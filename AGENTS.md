# Repository Entry Point

Use the repo-level Makefile as the single local entrypoint:

```bash
make help
make validate-all
make smoke-all
make validate EXP=<experiment>
make smoke EXP=<experiment>
make collect-results  # Aggregates all results/summary.json into docs/index.json
```

Available experiments (defined in Makefile): `postgresql-vs-mongodb`, `grpc-vs-rest`, `redis-vs-valkey`, `clickhouse-vs-postgresql`, `kafka-vs-rabbitmq`

# Experiment Structure

Each experiment lives in `experiments/<category>/<name>/` with:
- `README.md` - full experiment documentation
- `run.sh` - main experiment runner (supports `--clean`, `--smoke-only`, and sometimes `--keep-stack`)
- `results/` - output directory (raw per-target JSON + merged `summary.json`)

Example: `experiments/databases/postgresql-vs-mongodb/`

# Validation vs Smoke Tests

CI runs two stages (validation is a dependency of smoke):
- **Validation** (`scripts/validate-<exp>.sh`): checks runner syntax, `--help` output, Docker Compose config, runs tests via `go test ./...`
- **Smoke** (`scripts/smoke-<exp>.sh`): end-to-end run with small dataset (500-5000 items depending on experiment)

Some experiments validate multiple packages (e.g., `grpc-vs-rest` tests both `apps/bench-api` and `benchmarks/loadgen-http`).

Smoke tests require the infrastructure stack to start and tear down cleanly.

# Loadgen Organization

Benchmark binaries are in `benchmarks/loadgen-<type>/`:
- `loadgen-db` - database experiments (PostgreSQL vs MongoDB)
- `loadgen-http` - API experiments (gRPC vs REST)
- `loadgen-cache` - cache experiments (Redis vs Valkey)
- `loadgen-msg` - messaging experiments (Kafka vs RabbitMQ)
- `loadgen-analytics` - analytics experiments (ClickHouse vs PostgreSQL)
- `loadgen-k8s` - Kubernetes experiments

All loadgens require Go 1.23 (see each `go.mod`). Built binaries go to `bin/` subdirectory within each loadgen.

Some experiments require server components in `apps/` directory (e.g., `apps/bench-api` for grpc-vs-rest).

# Docker Compose Infrastructure

Infrastructure configs in `deployments/docker-compose/`:
- Root `docker-compose.yml` - shared services (PostgreSQL, MongoDB, exporters, Prometheus 9090, Grafana 3000)
- Category-specific subdirs: `api/`, `cache/`, `messaging/`, `analytics/`
  - Each category has its own Prometheus and Grafana instances to avoid conflicts
  - API: Prometheus 9096, Grafana 3004
  - Cache: Prometheus 9091, Grafana 3001
  - Messaging: Prometheus 9094, Grafana 3002
  - Analytics: Prometheus 9095, Grafana 3003

Default service ports: PostgreSQL (5432), MongoDB (27017), Kafka (9093), RabbitMQ (5672)
Default passwords: `benchpass` (override via `POSTGRES_PASSWORD` / `MONGO_PASSWORD` env vars)

Runners use `.env` files in compose directories if present (e.g., `deployments/docker-compose/.env`).

# Results Schema

Two standardized schemas:

1. **Per-experiment summary** (`results/summary.json`): follows `results-summary/v1` schema (see `docs/results-summary-v1.md`)
2. **Repo-level index** (`docs/index.json`): generated by `make collect-results`, follows `results-index/v1` schema (see `docs/results-index-v1.md`)

# Environment Variable Overrides

Standard overrides across experiments:
- `COUNT` / `INSERT_COUNT` - total items to insert
- `WORKERS` - concurrent workers
- `BATCH_SIZE` - batch size for inserts
- `SMOKE_COUNT` - items for smoke test
- `SMOKE_ONLY=true` - run smoke test only
- `SKIP_BUILD=true` - use existing binary, skip `go build`
- `KEEP_STACK=1` - keep Prometheus + Grafana running after benchmark (some experiments)

# Testing Loadgens

Run tests from each loadgen directory:

```bash
cd benchmarks/loadgen-db && go test ./...
cd benchmarks/loadgen-http && go test ./...
# etc.
```

Tests focus on percentile computation, report generation, and serialization.

# Common Gotchas

- **Docker Compose v2 required**: All run.sh files explicitly check for `docker compose` (v2), not `docker-compose` (v1)
- **Dependencies**: `jq` is always required, `docker` and `curl` for most experiments
- **Kafka initialization**: KRaft mode takes 30-60s to start; runners wait up to 5min
- **Port conflicts**: Check `lsof -i :<port>` before running experiments
- **First build**: Initial `go build` needs internet access to download Go modules
- **Go availability**: Runners check for Go, fall back to existing binaries if Go is unavailable (unless `SKIP_BUILD=true`)

# Key Notes

- **Smoke runs do NOT generate merged `summary.json`** - only full runs produce merged results
- **Runners handle service health checks** - explicit wait functions for each service (pg_isready, mongosh, kafka-topics, rabbitmq-diagnostics)
